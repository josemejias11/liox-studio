# TASK-0002: Analytics schema improvements + `/api/analytics/weak-topics` endpoint

## Goal
Store per-lesson view counts scoped to a course in Prisma, then expose a `POST /api/analytics/weak-topics` endpoint that identifies lessons with below-average engagement across all sessions and returns their topics as quiz `weakTopics`.

## Context
The AI quiz generator (`/api/quiz`) already accepts a `weakTopics: string[]` array to steer RAG question generation. Currently `MotoViewer.buildWeakTopics()` derives this only from the **current session's unvisited hotspots** — it has no population-level signal. The goal is to add cross-session analytics: which lessons do learners most often skip or view least? Those lesson topics become the `weakTopics` that make quizzes adaptive. Two data gaps block this: (1) `LessonProgress` has no `courseId`, making per-course aggregation impossible; (2) there is no view count — only a `completed` boolean and hotspot visit rows.

### New contract for `/api/analytics/weak-topics`

```ts
// POST /api/analytics/weak-topics
// Request body (browser sends lesson metadata so the server can map lessonId → topics):
export const WeakTopicsRequestSchema = z.object({
  courseId: z.string().min(1).max(100),
  lessons: z.array(z.object({
    id: z.string().min(1).max(100),          // lessonSection._key (same as LessonProgress.lessonId)
    headline: z.string().max(300),           // human-readable lesson title
    topics: z.array(z.string().max(200)),    // hotspot topics + headline words for quiz steering
  })).min(1).max(100),
});

// Response:
{
  weakTopics: string[],          // topics from below-median-engagement lessons, max 15
  engagement: Array<{            // sorted asc by viewCount (fewest-seen first)
    lessonId: string,
    viewCount: number,
  }>,
}
```

### Patterns in use
- Prisma schema lives at the repo root `prisma/schema.prisma`; run `npx prisma migrate dev --name <desc>` from inside `web/` after schema changes.
- After migration, run `npx prisma generate` to regenerate the client in `src/generated/prisma/`.
- API route files export named async functions (`GET`, `POST`).
- Validate all inbound payloads with Zod; return `{ error: string }` with appropriate HTTP status on failure.
- Import Prisma client via `import { prisma } from '@/lib/db'`.
- `contracts/api.ts` is the single file for non-quiz, non-Sanity API contracts.
- `contracts/quiz.ts` must NOT be touched.

### Known constraints
- `LessonProgress.lessonId` is the Sanity `_key` of the lesson section (a short hash string like `abc123`). It is NOT the Sanity document `_id`. Do not confuse these.
- Old `LessonProgress` rows have no `courseId` — default to `""` in the schema. Filter out `courseId: ""` rows in analytics queries so stale data doesn't skew results.
- The `@@id([sessionId, lessonId])` composite PK must remain unchanged (adding `courseId` to it would break existing rows and is not needed — the index is sufficient).
- The analytics dashboard at `/analytics` currently calls `getAnalyticsData()` — do not remove or rename that function's return shape. Add new exports alongside it.
- Do not add authentication to `/api/analytics/weak-topics` — it is called client-side from the course player, not the instructor dashboard.

## Requirements

1. **Schema**: Add `courseId String @default("")` and `viewCount Int @default(1)` to `LessonProgress`. Add `@@index([courseId, lessonId])`.
2. **Migration**: Generate and apply the Prisma migration (`prisma migrate dev`). Confirm the generated SQL only adds columns with defaults (zero downtime).
3. **Generate**: Run `prisma generate` so `src/generated/prisma/` is updated.
4. **Contract**: In `src/lib/contracts/api.ts`, add optional `courseId: z.string().min(1).max(100).optional()` to the `LessonProgressSchema` (the inner object, inside the discriminated union).
5. **Progress route**: In `src/app/api/progress/route.ts`, pass `courseId: body.courseId ?? ""` in both the `create` and `update` of the `lessonProgress.upsert`. On `update`, also increment `viewCount`: `{ courseId: body.courseId ?? "", viewCount: { increment: 1 } }`.
6. **Analytics service**: Add `export async function getLessonEngagement(courseId: string)` to `src/services/analytics.service.ts`. It should query `prisma.lessonProgress.groupBy({ by: ['lessonId'], where: { courseId, NOT: { courseId: "" } }, _sum: { viewCount: true } })` and return `Array<{ lessonId: string; viewCount: number }>` sorted ascending by `viewCount`.
7. **New endpoint**: Create `src/app/api/analytics/weak-topics/route.ts` exporting `POST`. It should:
   a. Parse the body with `WeakTopicsRequestSchema` (define this schema in `contracts/api.ts`).
   b. Call `getLessonEngagement(courseId)`.
   c. Compute the median viewCount across all lessons that have at least 1 row; treat un-seen lessons as viewCount 0.
   d. Identify lessons with `viewCount <= median` (the "weak" set).
   e. Return `{ weakTopics: string[], engagement: [...] }` where `weakTopics` is the union of all `topics` arrays for the weak lessons, deduplicated and capped at 15 items.
   f. If no engagement data exists yet (course is new), return `{ weakTopics: [], engagement: [] }`.
8. **Type-check**: `npx tsc --noEmit` passes with zero new errors.

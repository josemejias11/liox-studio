# TASK-0012: Course Material entries lost on sequential single-file uploads

## Goal
Uploading files one at a time across separate sessions appends each file to the persistent library — a `.docx` upload never replaces an existing `.xlsx` entry; only re-uploading the exact same filename (name + extension) updates an existing row.

## Context
After TASK-0010/0011, batch uploads (multiple files selected at once) appear correctly, but uploading one file and later uploading a different file (e.g. `.xlsx` then `.docx`) makes the first entry disappear from the panel. Assessment found the parser service is NOT at fault — ChromaDB chunk IDs hash `course_id|filename|chunk_index` and deletes are scoped `where={"source": filename}`, so chunks for different filenames coexist. The data loss happens in the Sanity patch layer of `CourseFileUploadInput.tsx`, which violates two hard Sanity requirements and has one stale-closure bug.

## Affected Area
- Layer: frontend (Sanity Studio custom input)
- Agent role: web-engineer

## Root Causes (assessed)

1. **Inserted items have no `_key`.** Sanity arrays of objects require a unique `_key` per member. The `insert` patch sends `{ _type: 'uploadedFile', filename, chunks, uploadedAt }` with no `_key`, so the form store cannot track item identity across patches/reconnects, the Studio flags "missing keys", and the keyed patches `set(..., [{_key: existing._key}])` / `unset([{_key: file._key}])` target `[{_key: undefined}]` — broken. React list keys (`key={f._key}`) are also all `undefined`.
2. **No `setIfMissing([])` before `insert`.** Against the content lake, `insert` into a path that doesn't exist is a no-op. The first single-file upload only ever lands in optimistic local form state; it never persists, so the next session's upload appears to "replace" it. Batch uploads look fine because all rows render from the same session's optimistic state.
3. **Stale closure on `indexedFiles`.** `handleFileChange` has deps `[courseId, onChange]` but reads `indexedFiles` (derived from `props.value`). The same-filename dedup check compares against the list captured when the callback was created, not the current value.

### Patterns in use
- Patches in custom inputs are dispatched via `onChange(PatchEvent.from(...))`; `PatchEvent.from` accepts multiple patches applied in order — bundle `setIfMissing([])` with the `insert` in one event.
- Paths are relative to the field, so `setIfMissing([])` (no path) initializes the `courseMaterial` array itself.
- Sequential uploads (no `Promise.all`) — keep the existing for-loop; single-instance Ollama must not be hit concurrently.
- `UploadedFile` type already declares `_key: string` — the fix makes reality match the type.

### Known constraints
- **Dedup key is the exact filename including extension** (`file.name`). `specs.xlsx` and `specs.docx` are distinct entries; only re-uploading `specs.xlsx` updates the `specs.xlsx` row. Do not compare basenames without extension.
- Do not change the `courseMaterial` schema, the parser service, or the Next.js routes — they are correct.
- The within-loop dedup must also see rows inserted earlier in the same loop (track appended files locally, e.g. a mutable map seeded from the latest `indexedFiles`), since `props.value` may not re-render mid-loop.
- Keep remove non-blocking (ChromaDB delete failure must not prevent the `unset`).

## Requirements
1. Every inserted `uploadedFile` member carries a unique `_key` generated with `randomKey()` from `@sanity/util/content`.
2. The insert patch event includes `setIfMissing([])` before `insert(...)` so the first upload persists when the array doesn't exist yet.
3. `handleFileChange` reads the current `indexedFiles` (fix the dependency array, and track same-loop insertions) so same-filename dedup works across renders and within a batch.
4. Sequential uploads of different filenames/extensions accumulate: upload `a.xlsx`, then `b.docx` in a separate action — both rows persist after a Studio reload.
5. Re-uploading the same filename still updates its row in place (no duplicate) and ✕ still removes the correct row (keyed `unset` now resolves).
6. `npm run typecheck` passes with no new errors.

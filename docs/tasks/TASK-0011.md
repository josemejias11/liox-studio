# TASK-0011: File deletion from ChromaDB + version deduplication on re-upload

## Goal
Removing a file from the Course Material panel also purges its chunks from ChromaDB, and re-uploading a file with the same name updates the existing Sanity record (no duplicate rows) while the parser service already replaces the chunks.

## Context
Two gaps exist after TASK-0010:

1. **Delete gap**: The ✕ remove button calls `PatchEvent.from(unset([{_key}]))` — removes the Sanity metadata row but leaves the file's chunks in ChromaDB. The AI keeps answering from stale content as if the file was never removed.

2. **Re-upload gap**: `parser-service/main.py` line 360 already does `vectorstore._collection.delete(where={"source": filename})` before inserting new chunks — so ChromaDB is correctly updated. But `CourseFileUploadInput` always appends a new Sanity record, so the persistent list shows duplicate rows for the same filename.

Neither a delete API endpoint nor a Next.js proxy for deletion exist yet. They need to be added end-to-end: parser service → Next.js route → Sanity Studio component.

## Affected Area
- Layer: API (parser service + Next.js proxy) + frontend (Sanity Studio component)
- Agent role: web-engineer

def delete_document(request: DeleteDocumentRequest):
    # If course has no collection, nothing to delete — return 200 silently.
    if not collection_exists(request.course_id):
        return {"status": "not_found", "filename": request.filename}
    vs = get_vectorstore(request.course_id)
    vs._collection.delete(where={"source": request.filename})
    # Evict from in-memory cache so next request rebuilds without stale metadata.
    with _vectorstores_lock:
        _vectorstores.pop(request.course_id, None)
    return {"status": "deleted", "filename": request.filename}

### Patterns in use
- `parserDelete` mirrors `parserPost` exactly — same auth header (`X-Internal-Token`), same `ParserServiceError` on non-2xx, same `AbortSignal.timeout`. Only difference: `method: 'DELETE'`, body is always JSON (no FormData path).
- The `DELETE` handler in `/api/upload/route.ts` follows the same guard pattern as `POST`: parse body, validate `course_id` and `filename` are non-empty strings, call `parserDelete`, return 502 with user-safe message on `ParserServiceError`.
- FastAPI `@app.delete` with a Pydantic JSON body: use `request: DeleteDocumentRequest` as the parameter (FastAPI reads the body automatically for DELETE with JSON content-type).
- `_vectorstores.pop(course_id, None)` must be inside `_vectorstores_lock` — same pattern as `get_vectorstore`.
- `set(newValue, path)` from `sanity` sets a value at a nested path. `[{_key: 'abc'}]` selects the array item by key. This replaces the whole object at that key, so spread the existing fields and override only what changed.

### Known constraints
- **Remove is non-blocking on API failure**: if the parser service is down, the ✕ button still removes the Sanity record (editor intent is clear). Log the error but proceed.
- **Do not add a confirmation dialog** — the remove button acts immediately.
- **Do not evict ALL collections from `_vectorstores`** — only `_vectorstores.pop(request.course_id, None)`.
- FastAPI `@app.delete` does accept a JSON body — this is valid HTTP even though some proxies strip it. The internal service never goes through an external proxy, so it's fine.
- `filename` in the Sanity record is the original client filename (`file.name`) — it must exactly match the `source` metadata stored in ChromaDB (set in `main.py` line 364 as `original_filename`). Do not normalize or truncate it.
- Keep the `require_internal_token` dependency on the new FastAPI endpoint.

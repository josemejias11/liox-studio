# TASK-0001: Improve RAG chat answer quality (with a measurable eval signal)

**Status:** done (2026-06-15) — results: [TASK-0001-results.md](./TASK-0001-results.md)

## Goal
Measurably improve the relevance and faithfulness of `/api/chat` answers by tuning the retrieval + generation pipeline in `parser-service/main.py`, gated behind a small repeatable eval harness so every change is justified by a number, not a hunch.

## Context
The RAG pipeline already works end-to-end: the browser calls Next's `/api/chat` proxy, which forwards to the self-hosted FastAPI parser service. The parser does cosine similarity retrieval from a per-course ChromaDB collection, filters by a relevance threshold, and asks a local Ollama `llama3` model to answer strictly from context. The pipeline is mature and safe (no-hallucination prompt, no-materials/no-context fallbacks) but **untuned and unmeasured** — there is no eval signal, so the threshold (`0.45`), retrieval `k` (`5`), chunking (`1000/200`), and prompt were set by eyeballing. This task adds a lightweight eval harness first, then uses it to drive concrete quality improvements. Do not regress the answer-isolation or no-hallucination guarantees.

## Affected Area
- Layer: cross-cutting (primarily the Python parser service; minor web contract touch only if richer `sources` are added)
- Agent role: ai-ml-engineer

### Patterns in use
- Parser service is **server-to-server only**, guarded by `X-Internal-Token` (`require_internal_token`). The eval harness runs in-process / against a local instance — it must not bypass or weaken auth.
- Pydantic models are the cross-service contract on the Python side; Zod schemas mirror them on the web side. Keep them in lockstep.
- Env-var-with-default config style (`os.environ.get(...)`). New tunables (e.g. `CHUNK_SIZE`, `CHUNK_OVERLAP`) should follow this pattern so they're adjustable without code edits.
- Relevance scores are cosine in `[0,1]`, higher = more similar. Existing measured ranges: on-topic ~0.55–0.70, off-topic ~0.40–0.50.
- No comments unless the WHY is non-obvious.

### Known constraints — a review will reject changes that ignore these
- **Do NOT weaken the no-hallucination guarantee.** Rule 2 of the chat prompt (output EXACTLY `NO_CONTEXT_ANSWER` when context is insufficient) and the post-generation `NO_CONTEXT_ANSWER` check must remain. Faithfulness is a first-class eval metric, not a tradeoff.
- **Chunking changes only take effect on re-upload** (chunks are written at upload time with deterministic IDs). The eval harness must (re)ingest its corpus after any chunk-size change, or it will measure stale chunks.
- **`course_id` must satisfy `COURSE_ID_PATTERN`** (3–63 chars, alnum at both ends). Eval course ids must conform.
- **If `sources` shape changes**, update `ParserChatResponseSchema` (parser-service.ts) and `ChatResponseSchema` (api.ts) in the same commit, plus any consumer (`CourseChat`, `DiscoveryPanel`). If in doubt, keep `sources: string[]` and defer enrichment to a follow-up task.
- The web `npm run typecheck && npm run test` gate still applies if any web file is touched.

## Requirements
1. **Eval harness.** Add a small, repeatable eval script under `parser-service/` (e.g. `parser-service/eval/`) that: ingests a fixed sample corpus into a dedicated eval course collection, runs a fixed set of question→expected-behavior cases, and reports per-config metrics. Cases must cover: on-topic answerable, off-topic (must return `NO_CONTEXT_ANSWER`), and no-materials (must return `NO_MATERIALS_ANSWER`).
2. **Metrics.** Report at minimum: retrieval hit-rate (did the relevant chunk make it into context above threshold), faithfulness (answer grounded in retrieved context / no hallucination), and correct-refusal rate (off-topic + no-context cases answered with the canonical fallback, not a fabricated answer). Document how each is computed.
3. **Baseline.** Record current-config metrics as the baseline before changing any tunable.
4. **Tuning, evidence-driven.** Sweep and select values for `RELEVANCE_THRESHOLD`, `RETRIEVAL_K_CHAT`, and chunk `size`/`overlap`. Promote a new default only if it beats baseline on the harness without lowering correct-refusal rate. Expose chunk size/overlap as env vars (`CHUNK_SIZE`/`CHUNK_OVERLAP`) following the existing config pattern.
5. **Prompt refinement (optional, gated).** If a prompt change improves faithfulness/conciseness on the harness, apply it; otherwise leave the prompt unchanged. No speculative edits.
6. **Document results.** Write a short results note (baseline vs. chosen config, the deltas, and the final chosen defaults + rationale) into the task's completion section or a sibling `docs/tasks/TASK-0001-results.md`.
7. **No scope creep.** Streaming, multi-turn history, and richer source snippets are explicitly out of scope (separate tasks). Touch the web layer only if a metric-justified `sources` enrichment is adopted — and then honor the contract-parity rule.
